# Viva questions and honest answers

Written for someone who will be questioned on this project. The answers say what was done, what was measured, and where the
limits are. Where an answer is "we did not verify that", that is the answer to give.

## The project

**What is it, in one sentence?** A forecasting, anomaly-detection and decision-support platform: it is validated on a full
year of real New York taxi data, and it runs the same pipeline as a real-time platform for Pune on simulated demand, with
every number labelled by what kind of data it is and how fresh it is.

**Why Pune if there is no Pune data?** Because the interesting engineering (live ingestion, freshness, failure handling,
a map-based console, a phone app) does not depend on the demand being real, and pretending it was real would be worse
than admitting it. The three real inputs are rain, the holiday calendar and the geography; demand is a model.

**Isn't simulated demand just making things up?** It is generated by a documented model whose assumptions are in one file and
are printed in the API. It is labelled SIMULATED on every screen. What it cannot do is tell you anything about real Pune
traffic, and the project never claims it does. What it can do is exercise every part of the pipeline against data whose
true structure is known, which real data never allows.

**What is actually live?** Weather (a 15-minute model step), modelled air quality (hourly) and recent rain, polled from
Open-Meteo. Nothing in Pune is "LIVE" in the strict sense of seconds-old observations; no such source exists.

## Data and modelling

**What did you check about Pune data sources?** Open-Meteo (forecast, air quality, archive) and Overpass were called and their
responses inspected. PMPML, the Pune Metro and the municipal portal were checked for open APIs and licences and none was found
(the portal had no API; the community PMPML GTFS has no stated data terms). TomTom and OpenAQ need keys and were not called.
Each is recorded in `PUNE_DATA_SOURCES.md` with what was verified.

**How are the zones defined?** Each zone is the region closest to one OpenStreetMap suburb (a Voronoi cell) clipped to the
study box: 91 zones from 134 place nodes after removing non-ASCII names and near-duplicates. They are not wards. The cell
areas sum to the box area (1050.4 against 1050.3 km²), and each seed lies in its own cell (tested).

**How is demand generated, and why that way?** A gravity model: hubs (business, transit, leisure) attract trips with
distance decay, hour-of-day profiles differ by zone type, weekends and holidays change them, rain lifts demand 6% per mm.
Counts are Poisson. The choice of a fixed uniform draw per cell through the Poisson quantile function means new rain data
changes only the cells whose rate changed; an earlier version drew counts directly and reshuffled the rest of the day.

**What forecasting model, and how is it validated?** LightGBM with a Poisson objective, features from days strictly before
the forecast origin (proved by test), walk-forward evaluation over held-out days, and a conformal 80% interval. On simulated
Pune demand it reaches WAPE 19.5% against 22.8% for the best baseline, with 79.6% interval coverage. On real New York data
(full 2024) it reaches 19.5% against 26.3%, and most of that gap is in holiday weeks, which is stated in the evaluation.

**Why does the Pune forecast look too high today?** The model has no weather input. Recent days were rainy, rain lifts
simulated demand, and today is dry, so the day-ahead forecast (built from recent days) is about 12% high. This is a real
limitation, visible in the console.

**How do you know the forecast does not leak the future?** Features use only days strictly before the forecast origin, a
test checks that, and evaluation is chronological (walk-forward), never a random split.

**What are the events, and are they accurate?** A rule on today's completed hours (documented in `LIVE_DATA.md`). It is
applied to simulated demand with planted events, so it can show the rule works but cannot show it would find real incidents.
On New York data the anomaly detector's precision is explicitly UNVERIFIED because real data has no labels.

## Architecture

**Why SQLite and not Postgres or Redis?** One writer, few readers, small volume, one machine. Postgres or Redis would add
services to run and secure without adding capability the workload needs (ADR-018). It does not scale out; that is a stated
limit and the point at which the decision should be revisited.

**Why a separate worker?** Ingestion must run without viewers, must not share a crash domain with the API, and needs a
single writer. The API never calls a data source, so a slow provider cannot slow a request.

**How is freshness computed?** From the source's own timestamp against how often it should update: 2.5x LIVE, 5x DELAYED, 12x
STALE (ADR-020). It catches a provider that repeats an old value while our poller looks healthy, which a poller-set flag cannot.

**What happens when a source fails?** The failure is recorded (error text, failed polls in a row), retried with exponential
backoff capped at the source's interval, and the last values stay on screen marked STALE then OFFLINE. Nothing is invented.
Tested with recorded responses: HTTP errors, invalid JSON, timeouts, a crashing job, a missing model.

**How does real-time delivery work and what happens when it drops?** Server-sent events: a full snapshot on connect, another
when the store changes, a heartbeat every 10 s. Clients reconnect with backoff and restart a silent connection after 30-45 s. The
console and the app show a "not current" notice with the time of the numbers they still hold. Tested in a real browser with the
network cut and restored, and on an emulator with the server killed and restarted.

**What did you find when you tested shutdown?** That the server did not stop: uvicorn waits for open event streams, and a connected
viewer never ends one, so `docker stop` would wait and then kill it. Graceful shutdown is now bounded (5 s), and the worker,
as PID 1, needed its own signal handler (it took 10.1 s and was killed; now 0.3 s). Both are regression-tested.

## Quality and honesty

**What is not verified?** A public domain deployment (none exists); the Android app on a physical phone; `docker compose up`
itself (plugin not installed here); the optional traffic and station air-quality sources (no adapters); real-Pune accuracy of
anything; LLM-mode analyst quality (no key). See the README's status section and `LIMITATIONS.md`.

**How many tests, and what do they cover?** Python: the whole pipeline, API, worker, store, freshness, simulator, live layer,
readiness, security and hostile inputs, at 95% line coverage; web: component and unit tests plus 24 browser tests with WCAG A/AA
scans in both themes; Android: 45 unit tests, lint clean. The tests found several real defects in this work (sampling
reshuffling, the wall-clock timestamp, the shutdown hang), which is the argument for having them.

**What would you do next?** Pick one real source of demand (a partner's trip data, or PMPML if it publishes one) and replace the
simulator behind the same interface; add weather features to the forecast; deploy behind a real domain and confirm the phone app
over HTTPS; write the traffic adapter after reading TomTom's terms on caching.
